# Ledger epoch, checkpoint, archive, and replay-barrier v3 contract vectors

These fixtures freeze the contract-only boundary owned by `src/memory_contracts/ledger_epoch.rs`. Every `.jsonl` file contains one canonical JSON record plus exactly one repository-framing LF; the LF is excluded from every digest. None of the epoch, checkpoint, manifest, or receipt bytes carries runtime authority — they are byte-exact structural fixtures, not activated state.

## What each fixture proves

- `successor-log-epoch.jsonl` — a `SuccessorLogEpochV1`: a new deterministic partition recipe (`ostk.partition.sha256_prefix64_modulo`, seed `0x09` repeated, 32 shards) minted because the shard count changed, bound to its exact predecessor epoch and the closed shard-head vector that predecessor was fenced at (two shards, 0 and 5, each with a last committed offset and append-chain digest). `SuccessorLogEpochV1::epoch_id()` under domain `ostk-log-epoch-v2` is pinned as `1f8c197c5854fed8980db82d88f82f568ba7005da4ed6096a935b6d02e8429c2`. Proves **REPLAY-01** (epoch identity is a deterministic function of predecessor, recipe, and closed vector) and the doc's "changing the shard count creates a new log epoch and checkpoint; evidence IDs do not change" rule — exercised by `shard_count_change_keeps_evidence_ids_unchanged`, which shows a different `shard_count` changes `epoch_id()` while `LostFenceRetryV1::accepted_event_id` has no path by which either epoch's shard count could reach it.
- `evidence-compaction-checkpoint.jsonl` — an `EvidenceCompactionCheckpointV1` whose `core` (retained-evidence manifest root, tombstone-set root, closed shard positions, append-chain root, segment-manifest root, retained-snapshot digest) hashes under domain `ostk-evidence-compaction-checkpoint-v1` to `8db62c9381cc2a2e47855015adfe85baee5ab5a6980d3f7142e2c82499b83eef`, which the embedded `replay_verification_receipt.verified_subject_digest` reproduces exactly. Proves **EVID-01** (the checkpoint accounts for retained evidence and tombstones rather than silently discarding either) and gates `VerifiedReplayAnchorV1` — the only way to anchor a `ReplayHorizonV1`.
- `cursor-vector-barrier.jsonl` — a standalone `CursorVectorBarrierV1` (two shard cursors) whose digest under `ostk-cursor-vector-v1` is order-independent: `cursor_vector_barrier_is_order_independent` rebuilds it with shard order reversed-then-resorted and shows the digest — and the `ProjectionGenerationV1::generation_id()` built from it — do not change. Proves REPLAY-01/REPLAY-02's "same facts under a different shard schedule ⇒ same generation" and "reversed arrival across shards produces the same generation."
- `projector-checkpoint.jsonl` — a `ProjectorCheckpointV1` reusing the same cursor-vector content, bound to one projector ID/version and registry digest. Its canonical field set (`projector_id`, `projector_version`, `registry_digest`, `cursor_vector`, `output_digest`, `verification_receipt`) is disjoint from `EvidenceCompactionCheckpointV1`'s (`core`, `replay_verification_receipt`), so `evidence_compaction_and_projector_checkpoints_are_not_interchangeable` shows each fixture's bytes fail `decode_strict` as the other type — a projector checkpoint can never be presented as evidence authority, structurally, not just by convention.
- `archive-move-admission.jsonl` — an `ArchiveMoveAdmissionV1` binding one `ArchiveSegmentManifestV1` (digest `13269e974c56de1985af23bf0ce1ab8c048ef676d2ef8eac1182838de0d95086` under `ostk-archive-segment-manifest-v1`) to a `DurableCopyReceiptV1` naming that exact manifest digest and object digest, and a `ReplayVerificationReceiptV1` naming that same manifest digest. `archive_move_requires_every_admission_binding` shows perturbing either receipt's bound digest fails `validate()` and blocks `AdmittedArchiveMoveV1::from_admission` — the move-admission rule.
- `negative-unsorted-head-vector.jsonl` — a `ClosedHeadVectorV1` whose two shard heads (5 then 0) are well-formed but out of order. It decodes (the schema is valid) but `.validate()` fails with `ContractError::NonCanonicalSet { field: "heads" }`.
- `negative-missing-predecessor.jsonl` — the golden `successor-log-epoch.jsonl` bytes with `activation_binding.predecessor_epoch_id` removed. `EpochActivationBindingV1` has no optional or defaulted fields, so `decode_strict::<SuccessorLogEpochV1>` fails at the schema boundary.
- `negative-seed-shape.jsonl` — the golden `successor-log-epoch.jsonl` bytes with `partition_recipe.seed` truncated from 64 to 62 hex characters (still valid lowercase hex, wrong length). `FixedHex32`'s deserializer requires an exact-length hex string, so decode fails closed.

## How digests are pinned

Every digest in these fixtures is `SHA-256(domain_prefix_ascii || 0x00 || canonical_json_bytes)`, matching `digest::domain_separated_digest` exactly. The canonical JSON bytes are RFC 8785/JCS-style: object keys sorted by UTF-16 code unit order (equivalent to byte order for the all-ASCII keys used here), no insignificant whitespace, and every `CommittedOffsetV1`/`CanonicalDecimal`-typed field written as a quoted decimal string rather than a bare JSON number (see `"committed_offset":"1"` in `control.rs`'s own fixtures for the same convention). The fixtures here were generated with a short Python script replicating that exact algorithm (`json.dumps(obj, sort_keys=True, separators=(",", ":"))` over plain dicts/lists/strings, which is byte-identical to the Rust canonicalizer for this ASCII-only, float-free, control-character-free fixture set), and every embedded digest was independently recomputed the same way. Rust's own tests then close the loop: each positive fixture is `decode_strict`'d, `validate()`'d, and its `encode_canonical` output is asserted equal to the golden bytes, so any future edit that breaks byte-exactness or receipt/manifest binding fails the test, not just the Python generator.

`vector-suite.jsonl` aggregates every fixture's file name, purpose, and the invariant IDs it exercises, plus every pinned digest, in one line for quick auditing.

## Design note: why `activation_binding` nests the closed predecessor vector

The architecture doc lists an epoch's bound facts as "the domain-separated partition-hash recipe, seed, shard count, and predecessor epoch," and separately says "epoch activation atomically fences every old shard head at one closed vector." `SuccessorLogEpochV1` folds "predecessor epoch id" and "closed predecessor head vector" into one nested `EpochActivationBindingV1` field (rather than two independent top-level fields) so "this closed vector belongs to this predecessor" is a schema fact enforced by `EpochActivationBindingV1::validate` (which checks `closed_predecessor_head.epoch_id == predecessor_epoch_id`), not a convention two independently-mutable fields could silently drift apart on. `SuccessorLogEpochV1::predecessor_epoch_id()` and `::closed_predecessor_head()` remain available as direct accessors for callers that only want one half.

## Invariant IDs exercised

- **REPLAY-01** — replaying the same accepted events under the same registry/projector versions yields identical semantic identities. `SuccessorLogEpochV1::epoch_id()` is a pure function of profile/scope/recipe/predecessor/closed-vector bytes; `CursorVectorBarrierV1::barrier_digest()` and `ProjectionGenerationV1::generation_id()` are pure functions of sorted `(shard, offset)` pairs, so reversed shard arrival reproduces the same digest and the same generation.
- **REPLAY-02** — every projector advances its own cursor atomically with that stage's complete durable output. `ProjectorCheckpointV1` binds one projector ID/version/registry digest to one cursor vector and output digest; `ProjectionGenerationV1` requires `generation_sequence == 0` exactly when `supersedes` is absent, so a later (superseding) generation is always distinguishable from, and never overwrites, an earlier one.
- **EVENT-03** — evidence is accepted before or atomically with its projection; this module never fakes the append seam. `LostFenceRetryV1` carries exactly one `accepted_event_id` field for both the losing and retried physical position — there is no way to construct a retry with two different semantic identities for the same physical event.
- **EVID-01** — the accepted envelope is append-only. `EvidenceCompactionCheckpointCoreV1` requires `retained_evidence_manifest_root` and `tombstone_set_root` as non-optional fields, so a checkpoint that silently dropped retained evidence or tombstones would need to lie about them, not omit them, and `EvidenceCompactionCheckpointV1::validate` requires an independently reproduced `core_digest` to match the embedded receipt before `VerifiedReplayAnchorV1::from_checkpoint` will construct its private-field anchor.

## Reviewer's guide to breaking each rule

- **Epoch fence bypass**: try to construct an `AppendPositionV1` targeting a fenced predecessor epoch that `EpochFenceV1::reject_append_after_fence` accepts. It cannot: the check is `position.epoch_id == fence.predecessor_epoch_id()`, and `predecessor_epoch_id()` is derived from the fence's own `successor_epoch.activation_binding`, not caller-supplied.
- **Retry identity substitution**: try to make `LostFenceRetryV1::validate_against` accept a retry whose semantic identity differs from the losing append's. Impossible without also changing the losing append's identity, because both share the single `accepted_event_id` field.
- **Checkpoint/projector confusion**: try to make `VerifiedReplayAnchorV1::from_checkpoint` accept a `ProjectorCheckpointV1`. It does not compile — the function signature only accepts `&EvidenceCompactionCheckpointV1`.
- **Archive move without verification**: try to make `AdmittedArchiveMoveV1::from_admission` succeed when `replay_verification_receipt.verified_subject_digest` does not equal the manifest's own digest. `ArchiveMoveAdmissionV1::validate` checks that binding explicitly and fails closed.
- **Implicit unbounded replay**: try to construct a `ReplayHorizonV1` without naming `semantic_replay_from`. Both fields are mandatory, non-defaulted, and `#[serde(deny_unknown_fields)]`; there is no `Default` impl.
