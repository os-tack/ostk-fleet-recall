# Ledger epoch, checkpoint, archive, and replay-barrier v3 contract vectors

These fixtures freeze the contract-only boundary owned by `src/memory_contracts/ledger_epoch.rs`. Every `.jsonl` file contains one canonical JSON record plus exactly one repository-framing LF; the LF is excluded from every digest. None of the epoch, checkpoint, manifest, or receipt bytes carries runtime authority — they are byte-exact structural fixtures, not activated state.

## What each fixture proves

- `successor-log-epoch.jsonl` — a `SuccessorLogEpochV1`: a new deterministic partition recipe (`ostk.partition.sha256_prefix64_modulo`, seed `0x09` repeated, 32 shards) minted because the shard count changed, bound to its exact predecessor epoch and the closed shard-head vector that predecessor was fenced at (two shards, 0 and 5, each with a last committed offset and append-chain digest). `SuccessorLogEpochV1::epoch_id()` under domain `ostk-log-epoch-v2` is pinned as `1f8c197c5854fed8980db82d88f82f568ba7005da4ed6096a935b6d02e8429c2`. Proves **REPLAY-01** (epoch identity is a deterministic function of predecessor, recipe, and closed vector) and the doc's "changing the shard count creates a new log epoch and checkpoint; evidence IDs do not change" rule — exercised by `shard_count_change_keeps_evidence_ids_unchanged`, which shows a different `shard_count` changes `epoch_id()` while `LostFenceRetryV1::accepted_event_id` has no path by which either epoch's shard count could reach it.
- `evidence-compaction-checkpoint.jsonl` — an `EvidenceCompactionCheckpointV1` whose `core` (retained-evidence manifest root, tombstone-set root, closed shard positions, append-chain root, segment-manifest root, retained-snapshot digest) hashes under domain `ostk-evidence-compaction-checkpoint-v1` to `8db62c9381cc2a2e47855015adfe85baee5ab5a6980d3f7142e2c82499b83eef`, which the embedded `replay_verification_receipt.verified_subject_digest` reproduces exactly. Proves **EVID-01** (the checkpoint accounts for retained evidence and tombstones rather than silently discarding either) and gates `VerifiedReplayAnchorV1` — the only way to anchor a `ReplayHorizonV1`.
- `cursor-vector-barrier.jsonl` — a standalone `CursorVectorBarrierV1` (two shard cursors) whose digest under `ostk-cursor-vector-v1` is pinned as `231b09eb8bb020d4e7fa5fb6d17bac004e67d2d3a7ca912b805f71ec408252c4`, and is genuinely order-independent: `cursor_vector_barrier_is_order_independent` feeds the same per-shard observations to the normalizing constructor `CursorVectorBarrierV1::from_observations` in reversed arrival order and shows the resulting digest — and the `ProjectionGenerationV1::generation_id()` built from it — match the golden fixture's. This proves "reversed arrival across shards produces the same generation" against a real construction-order difference, not a sort-then-resort no-op. It does **not** by itself prove schedule-independence across a *different* shard count/schedule (same shard set, different arrival order, is a narrower property) — see `projection_generation_identity_is_independent_of_shard_schedule` below for that.
- `projection-generation.jsonl` — the `ProjectionGenerationV1` published from `cursor-vector-barrier.jsonl`'s barrier (`generation_sequence: 0`, `supersedes: null`). `generation_id()` under domain `ostk-projection-generation-v1` is pinned as `5d619c49cfceb87413a7dfb437feb0ab90ed5901918b9afc400b664b442dac82`. Identity is computed over `(schema_version, projector_id, projector_version, output_digest)` only — `barrier`, `generation_sequence`, and `supersedes` are all deliberately excluded from the hash preimage, because all three are shard-schedule artifacts rather than published facts: `barrier` is a physical coordinate outright, and `generation_sequence`/`supersedes` record how many intermediate generations a schedule needed to reach the published facts, which itself depends on the schedule. (An earlier round of this fixture excluded only `barrier` from identity; a review showed that insufficient — see the note below.) `projection_generation_identity_is_independent_of_shard_schedule` proves the full claim: a one-generation schedule (sequence 0, no predecessor — the golden record) and an unrelated two-generation schedule's *final* record (sequence 1, superseding an arbitrary earlier generation, over a genuinely different barrier and epoch) that reach the same total facts (`output_digest`) produce the *identical* `generation_id()`, which is REPLAY-01's "same facts under a different shard schedule ⇒ same generation" exercised against a real difference in publication history, not merely a relabeled barrier. `projection_generation_supersession_binds_projector_identity_and_sequence` pins the three cross-record checks `validate()` alone cannot make: a generation from a *different projector* (or a differing `projector_version`) can never supersede this one even with a strictly-advanced barrier and the correct predecessor id; and a superseding generation's `generation_sequence` must be *exactly* the predecessor's plus one — a lower, equal, or skipped sequence is rejected. `cursor_vector_barrier_is_order_independent` additionally pins that a superseding generation over the *same* barrier with a different `output_digest` is rejected by `ProjectionGenerationV1::validate_supersession`, and that a superseding generation over a *strictly advanced* barrier (one shard's offset increases, none regress) is accepted while the earlier generation's own record and id remain valid.

  **Correction (this round):** a prior round's identity preimage excluded only `barrier` and kept `generation_sequence`/`supersedes` in the hash. That is insufficient: those two fields are themselves shard-schedule artifacts (a finer-grained schedule can need an extra intermediate generation — a higher `generation_sequence` and a non-null `supersedes` — to cover the identical total facts a coarser schedule reaches as generation 0). The prior round's own committed test only ever varied `barrier` while holding `generation_sequence`/`supersedes`/`output_digest` fixed via struct-update syntax, which proves barrier-exclusion (true by construction, cannot fail) but not schedule-independence. `generation_id()` and `ProjectionGenerationIdentityV1` now drop both fields from the preimage, and `projection_generation_identity_is_independent_of_shard_schedule` now varies `generation_sequence`/`supersedes` directly, not just `barrier`.
- `projector-checkpoint.jsonl` — a `ProjectorCheckpointV1` reusing the same cursor-vector content, bound to one projector ID/version and registry digest, with its `verification_receipt.verified_subject_digest` bound to its own `output_digest` (mirroring how `EvidenceCompactionCheckpointV1` binds its receipt to `core_digest`). `checkpoint_digest()` under domain `ostk-projector-checkpoint-v1` is pinned as `8a44db6d8037225760678ea51a8f55db2fd6be63c0202cead1f2405e39fd333d`. Its canonical field set (`projector_id`, `projector_version`, `registry_digest`, `cursor_vector`, `output_digest`, `verification_receipt`) is disjoint from `EvidenceCompactionCheckpointV1`'s (`core`, `replay_verification_receipt`), so `evidence_compaction_and_projector_checkpoints_are_not_interchangeable` shows each fixture's bytes fail `decode_strict` as the other type — a projector checkpoint can never be presented as evidence authority, structurally, not just by convention. `projector_checkpoint_digest_can_never_satisfy_a_semantic_replay_anchor` goes further: it takes this fixture's real `checkpoint_digest()`, writes it into a `ReplayHorizonV1.semantic_replay_from`, round-trips it through `encode_canonical -> decode_strict` (the exact wire path a runtime uses), and shows `validate_semantic_anchor` rejects it both with no anchor and with a real anchor derived from a *different* (evidence-compaction) checkpoint.
- `archive-move-admission.jsonl` — an `ArchiveMoveAdmissionV1` binding one `ArchiveSegmentManifestV1` (digest `13269e974c56de1985af23bf0ce1ab8c048ef676d2ef8eac1182838de0d95086` under `ostk-archive-segment-manifest-v1`) to a `DurableCopyReceiptV1` naming that exact manifest digest and object digest, and a `ReplayVerificationReceiptV1` naming that same manifest digest. `archive_move_requires_every_admission_binding` shows perturbing either receipt's bound digest fails `validate()` and blocks `AdmittedArchiveMoveV1::from_admission` — the move-admission rule.
- `negative-unsorted-head-vector.jsonl` — a `ClosedHeadVectorV1` whose two shard heads (5 then 0) are well-formed but out of order. It decodes (the schema is valid) but `.validate()` fails with `ContractError::NonCanonicalSet { field: "heads" }`. `closed_head_vector_from_heads_normalizes_and_rejects_duplicates` additionally shows `ClosedHeadVectorV1::from_heads` normalizes genuinely reversed input into the same golden vector and rejects a duplicate shard, and `checkpoint_plus_tail_replay_reproduces_the_same_closed_vector` shows folding a tail of post-checkpoint shard advances onto `evidence-compaction-checkpoint.jsonl`'s closed positions (via `EvidenceCompactionCheckpointCoreV1::replay_tail`) reproduces byte-identical bytes to a from-genesis vector built directly with the same final shard state, that a tail entry regressing a shard the checkpoint already closed is rejected, that a tail entry naming an already-closed shard at the *identical* offset but a *different* `chain_digest` (a forked append chain) is rejected rather than silently substituted for the checkpoint's own closed head, and that the identical offset with the identical `chain_digest` (an idempotent re-observation) is accepted as a no-op.
- `negative-missing-predecessor.jsonl` — the golden `successor-log-epoch.jsonl` bytes with `activation_binding.predecessor_epoch_id` removed. `EpochActivationBindingV1` has no optional or defaulted fields, so `decode_strict::<SuccessorLogEpochV1>` fails at the schema boundary.
- `negative-seed-shape.jsonl` — the golden `successor-log-epoch.jsonl` bytes with `partition_recipe.seed` truncated from 64 to 62 hex characters (still valid lowercase hex, wrong length). `FixedHex32`'s deserializer requires an exact-length hex string, so decode fails closed.

## How digests are pinned

Every digest in these fixtures is `SHA-256(domain_prefix_ascii || 0x00 || canonical_json_bytes)`, matching `digest::domain_separated_digest` exactly. The canonical JSON bytes are RFC 8785/JCS-style: object keys sorted by UTF-16 code unit order (equivalent to byte order for the all-ASCII keys used here), no insignificant whitespace, and every `CommittedOffsetV1`/`CanonicalDecimal`-typed field written as a quoted decimal string rather than a bare JSON number (see `"committed_offset":"1"` in `control.rs`'s own fixtures for the same convention). The fixtures here were generated with a short Python script replicating that exact algorithm (`json.dumps(obj, sort_keys=True, separators=(",", ":"))` over plain dicts/lists/strings, which is byte-identical to the Rust canonicalizer for this ASCII-only, float-free, control-character-free fixture set), and every embedded digest was independently recomputed the same way. Rust's own tests then close the loop: each positive fixture is `decode_strict`'d, `validate()`'d, and its `encode_canonical` output is asserted equal to the golden bytes, so any future edit that breaks byte-exactness or receipt/manifest binding fails the test, not just the Python generator.

`vector-suite.jsonl` aggregates every fixture's file name, purpose, and the invariant IDs it exercises, plus **every one of the six `ostk-*` digests this workstream's `DigestDomain` variants produce** (`successor_log_epoch_id`, `evidence_compaction_core_digest`, `projector_checkpoint_digest`, `archive_segment_manifest_digest`, `cursor_vector_barrier_digest`, `projection_generation_id`), in one line for quick auditing. It is itself `include_bytes!`'d and decoded in `vector_suite_is_byte_frozen_and_advertises_every_pinned_digest`, which reconstructs it field-for-field in Rust and asserts `encode_canonical` reproduces the golden bytes exactly; `every_w0_log_digest_domain_is_pinned_by_a_hard_coded_hex_constant` independently re-derives all six digests from their own golden fixtures and compares them to hard-coded hex constants. Renaming any one of the six `DigestDomain::prefix()` strings in `digest.rs` changes exactly one re-derived digest and fails a test — this was verified directly: renaming `ostk-projector-checkpoint-v1`, `ostk-cursor-vector-v1`, and `ostk-projection-generation-v1` (the three domains a prior review found completely unfrozen) now fails 2 tests, and renaming the other three still fails 8.

## Design note: why `activation_binding` nests the closed predecessor vector

The architecture doc lists an epoch's bound facts as "the domain-separated partition-hash recipe, seed, shard count, and predecessor epoch," and separately says "epoch activation atomically fences every old shard head at one closed vector." `SuccessorLogEpochV1` folds "predecessor epoch id" and "closed predecessor head vector" into one nested `EpochActivationBindingV1` field (rather than two independent top-level fields) so "this closed vector belongs to this predecessor" is a schema fact enforced by `EpochActivationBindingV1::validate` (which checks `closed_predecessor_head.epoch_id == predecessor_epoch_id`), not a convention two independently-mutable fields could silently drift apart on. `SuccessorLogEpochV1::predecessor_epoch_id()` and `::closed_predecessor_head()` remain available as direct accessors for callers that only want one half.

## Invariant IDs exercised

- **REPLAY-01** — replaying the same accepted events under the same registry/projector versions yields identical semantic identities. `SuccessorLogEpochV1::epoch_id()` is a pure function of profile/scope/recipe/predecessor/closed-vector bytes; `CursorVectorBarrierV1::barrier_digest()` is a pure function of sorted `(shard, offset)` pairs, so reversed shard arrival — fed through the normalizing constructors `CursorVectorBarrierV1::from_observations`/`ClosedHeadVectorV1::from_heads` — reproduces the same digest. `ProjectionGenerationV1::generation_id()` goes further: its hash preimage is `(schema_version, projector_id, projector_version, output_digest)` only, deliberately *excluding* `barrier`, `generation_sequence`, and `supersedes` — all three are shard-schedule artifacts, not published facts, since the number of intermediate generations a schedule needs to reach a given total is itself schedule-dependent — so `projection_generation_identity_is_independent_of_shard_schedule` can build the identical publication over a genuinely different shard schedule *and* a genuinely different publication history (a one-generation schedule vs. the final record of a two-generation schedule reaching the same total facts) and show the generation id agrees exactly, the literal proof of "same facts under a different shard schedule ⇒ same generation." `EvidenceCompactionCheckpointCoreV1::replay_tail` shows checkpoint-plus-tail replay reaches byte-identical closed-vector bytes to a from-genesis replay reaching the same final shard state.
- **REPLAY-02** — every projector advances its own cursor atomically with that stage's complete durable output. `ProjectorCheckpointV1` binds one projector ID/version/registry digest to one cursor vector and output digest, and its verification receipt is bound to that exact `output_digest`. `ProjectionGenerationV1` requires `generation_sequence > 0` exactly when `supersedes` is present (single-record shape check only), and `ProjectionGenerationV1::validate_supersession` — the required second, cross-record check before admitting any superseding generation — additionally requires: the superseding generation names its exact predecessor's `generation_id`; it shares that predecessor's exact `projector_id` and `projector_version` (a generation is never superseded by a different projector, or a different version of the same one, by default); its `generation_sequence` equals the predecessor's plus exactly one (a lower, equal, or skipped sequence is rejected); and its barrier strictly dominates (same epoch, same shard set, every cursor `>=`, at least one `>`) the predecessor's. So publishing a different `output_digest` over the *same* closed barrier is rejected, a cross-projector or cross-version "supersession" is rejected, a sequence that regresses or skips is rejected, and a later (superseding) generation is always over strictly more evidence than, and never overwrites, an earlier one.
- **EVENT-03** — evidence is accepted before or atomically with its projection; this module never fakes the append seam. `LostFenceRetryV1` carries exactly one `accepted_event_id` field for both the losing and retried physical position — there is no way to construct a retry with two different semantic identities for the same physical event. `EpochFenceV1::reject_append_after_fence` is an allow-list (admit only `position.epoch_id == successor_epoch_id()` and `shard < successor shard_count`), not a deny-list of the one predecessor id, so an unknown/fabricated epoch id, a grand-predecessor epoch from an earlier cutover, and an out-of-recipe shard are all rejected, not just the immediate predecessor.
- **EVID-01** — the accepted envelope is append-only. `EvidenceCompactionCheckpointCoreV1` requires `retained_evidence_manifest_root` and `tombstone_set_root` as non-optional fields, so a checkpoint that silently dropped retained evidence or tombstones would need to lie about them, not omit them, and `EvidenceCompactionCheckpointV1::validate` requires an independently reproduced `core_digest` to match the embedded receipt before `VerifiedReplayAnchorV1::from_checkpoint` will construct its private-field anchor. `ReplayHorizonV1::validate_semantic_anchor` — the only public entry point that decides whether a decoded horizon may be trusted — requires that same `VerifiedReplayAnchorV1` whenever `semantic_replay_from` names a checkpoint, and a `ProjectorCheckpointV1`'s digest can never satisfy it (see the "Checkpoint/projector confusion" and "Semantic-anchor forgery" rows below).

## Reviewer's guide to breaking each rule

- **Forked append chain silently substituted during replay**: try to make `EvidenceCompactionCheckpointCoreV1::replay_tail` accept a tail entry naming a shard the checkpoint already closed, at the checkpoint's own `last_committed_offset`, but with a *different* `chain_digest`. Before this round it did — the guard compared only the offset, so `by_shard.insert` unconditionally overwrote the checkpoint's own closed head with the forked one, and a checkpoint-plus-tail replay could silently reach a different closed vector than a from-genesis replay of the same shard state (REPLAY-01, EVID-01). It now fails closed: `replay_tail` compares both offset and `chain_digest` for an already-closed shard, accepting only a strict offset advance (any `chain_digest`) or an exact `(offset, chain_digest)` match (an idempotent no-op); any other combination — same offset, different digest — is a fork, rejected as contested input. `checkpoint_plus_tail_replay_reproduces_the_same_closed_vector` pins all three cases: strict advance accepted, same-offset-different-digest fork rejected, and same-offset-same-digest no-op accepted and left unchanged.
- **Epoch fence bypass**: try to construct an `AppendPositionV1` that `EpochFenceV1::reject_append_after_fence` admits without naming exactly the fence's successor epoch and an in-range shard. It cannot: the rule is an allow-list — `position.epoch_id == fence.successor_epoch_id()` and `position.shard < successor_epoch.partition_recipe.shard_count` — derived entirely from the fence's own state, not caller input. `epoch_fence_is_an_allow_list_not_a_deny_list` pins rejection of a fabricated epoch id, a grand-predecessor epoch, the immediate predecessor, and an out-of-range shard, and acceptance of only the exact successor epoch at an in-range shard.
- **Retry identity substitution**: try to make `LostFenceRetryV1::validate_against` accept a retry whose semantic identity differs from the losing append's. Impossible without also changing the losing append's identity, because both share the single `accepted_event_id` field.
- **Checkpoint/projector confusion**: try to make `VerifiedReplayAnchorV1::from_checkpoint` accept a `ProjectorCheckpointV1`. It does not compile — the function signature only accepts `&EvidenceCompactionCheckpointV1`.
- **Semantic-anchor forgery**: try to make `ReplayHorizonV1::validate_semantic_anchor` accept a `Checkpoint` semantic bound carrying a `ProjectorCheckpointV1`'s `checkpoint_digest()`. `projector_checkpoint_digest_can_never_satisfy_a_semantic_replay_anchor` pins that this fails both with no anchor supplied and with a real anchor from an unrelated checkpoint; the only anchor this crate's public API can produce is `VerifiedReplayAnchorV1::from_checkpoint(&EvidenceCompactionCheckpointV1)`, and its `checkpoint_digest()` cannot equal a `ProjectorCheckpointV1`'s (a different digest domain) without a SHA-256 preimage collision. Note that `decode_strict`/schema validation alone does *not* reject the forged bytes — they are well-formed — so a caller must call `validate_semantic_anchor`, not merely decode successfully, before trusting a horizon.
- **Rewritten generation over an unchanged barrier**: try to make `ProjectionGenerationV1::validate_supersession` accept a superseding generation whose barrier is identical to its predecessor's. It cannot: dominance requires at least one shard's offset to strictly increase, so a same-barrier "later" generation with a different `output_digest` — the exact shape of the committed regression test this rule replaces — is rejected.
- **Cross-projector / cross-version supersession**: try to make `validate_supersession` accept a `self` whose `projector_id` or `projector_version` differs from the predecessor's, even with the correct predecessor id and a strictly-advanced barrier. It cannot: both are checked explicitly before the barrier is examined at all. `projection_generation_supersession_binds_projector_identity_and_sequence` pins both a differing `projector_id` and a differing `projector_version` returning `Err`; there is no default admission path for a projector-version bump, only room for a future workstream to add one as an explicit, separately named and separately tested rule.
- **Sequence regression, repetition, or skip**: try to make `validate_supersession` accept a `self.generation_sequence` that is not exactly the predecessor's plus one. `projection_generation_supersession_binds_projector_identity_and_sequence` builds a legitimate predecessor at `generation_sequence: 50` and pins that `1` (regression), `50` (repetition), and `52` (skip) are all rejected, while `51` is accepted — closing the hole where a consumer that orders published generations by `generation_sequence` could otherwise be made to read a strictly later generation as older.
- **Schedule-dependent generation identity**: try to make `generation_id()` differ for two publications that reach the same total facts (`output_digest`) over genuinely different shard schedules — including schedules that needed a different *number of intermediate generations* to get there, not merely a different `barrier`. It cannot: `barrier`, `generation_sequence`, and `supersedes` are none of them part of the hash preimage (see the type-level doc on `ProjectionGenerationV1` and its private `ProjectionGenerationIdentityV1` sibling). `projection_generation_identity_is_independent_of_shard_schedule` pins this directly — a one-generation schedule (sequence 0, no predecessor) and the *final* record of an unrelated two-generation schedule (sequence 1, superseding an arbitrary earlier generation, over a genuinely different barrier and epoch, confirmed via `assert_ne!` on `barrier_digest()`) both yield the *same* `generation_id()` once `output_digest` agrees. An identity that varies only `barrier` while holding `generation_sequence`/`supersedes` fixed does not establish this — it proves barrier-exclusion, which is true by construction — which is why this test now varies the publication history itself.
- **Archive move without verification**: try to make `AdmittedArchiveMoveV1::from_admission` succeed when `replay_verification_receipt.verified_subject_digest` does not equal the manifest's own digest. `ArchiveMoveAdmissionV1::validate` checks that binding explicitly and fails closed.
- **Implicit unbounded replay**: try to construct a `ReplayHorizonV1` without naming `semantic_replay_from`. Both fields are mandatory, non-defaulted, and `#[serde(deny_unknown_fields)]`; there is no `Default` impl.
- **Unknown-field smuggling through `ReplayFrom::Genesis`**: try to decode `{"kind":"genesis","evil":"payload"}` into a `ReplayFrom` and have it succeed. Before this round it did: serde's `#[serde(deny_unknown_fields)]` on an internally tagged enum (`#[serde(tag = "kind")]`) has no effect on a *unit* variant — it is deserialized by a `void` visitor that never inspects a payload, so the unknown field was silently dropped and `Genesis` decoded successfully. `Genesis` is now the empty *struct* variant `Genesis {}`, which goes through serde's normal field-checking machinery exactly like `Checkpoint` already did, with no change to the wire bytes (`{"kind":"genesis"}` either way — an empty struct variant and a unit variant serialize identically under internal tagging). `replay_from_genesis_unit_variant_rejects_unknown_fields` pins the exact runtime decode path (`decode_strict::<ReplayHorizonV1>`) rejecting the smuggled field in both `semantic_replay_from` and `historical_content_available_from`, alongside a byte-for-byte round-trip proof that the honest `{"kind":"genesis"}` fixture bytes are unchanged.
